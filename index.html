📐 Phase 1：产品规划 — 先想清楚再动手

产品思维的核心不是"怎么做"，而是"做什么"和"为什么做"。在让 AI 写任何代码之前，我花了大量时间定义问题、设计框架、拆解模块。AI 是执行力极强的工具，但方向必须由产品思维来定。

1

明确业务目标

为什么需要这个平台？解决什么痛点？

2

定义用户角色

谁用？怎么用？权限怎么分？

3

设计功能架构

模块怎么拆？数据怎么流转？

4

选择技术底座

自研还是基于开源？为什么？

5

制定验收标准

什么算"做完了"？怎么衡量？

🎯 业务目标定义

团队需要对飞行采集的地图数据进行标注（道路、建筑、植被、车辆等），原有方式是单机版工具 + 手动传文件，存在严重瓶颈：

  • 效率瓶颈：单机工具无法多人协作，10 个标注员排队等一台机器
  • 质量失控：没有审核流程，标完就交，错误率高达 15%
  • 进度黑盒：管理者无法实时看到每个项目的标注进度
  • 数据孤岛：标注结果散落在各台电脑，汇总靠手动拷贝

核心诉求提炼：一个支持多人协作、有审核流程、可追踪进度、数据自动闭环的在线标注平台。

🧩 模块拆解思路：为什么这样分？

  • 按用户旅程拆：登录 → 选项目 → 领任务 → 标注 → 提交 → 审核 → 导出，每个环节是一个独立模块
  • 按变更频率拆：UI 层改动最频繁，业务层次之，基础设施层最稳定。分开后改 UI 不影响底层
  • 按验收难度拆：每个模块可以独立演示和验收。"标注工作台"做完就能让标注员试用
  • 按 AI 对话粒度拆：一次对话解决一个模块的一个功能点。太大 AI 会丢失上下文，太小效率低
🔑 技术选型决策：为什么选 CVAT？
✗
方案 A：完全自研
标注工具涉及 Canvas 渲染、帧同步、坐标变换等复杂交互，自研周期至少 3-6 个月。
✗
方案 B：LabelImg / LabelMe 等轻量工具
只支持单机、单人、图片标注。无协作、无审核、无视频支持。不满足核心需求。
✗
方案 C：商业 SaaS（Labelbox / Scale AI）
数据必须上传到第三方服务器，飞行数据涉密，安全合规不允许。
✓
方案 D：CVAT 开源二次开发 ✅
Intel 开源、社区活跃（GitHub 12k+ star）、功能覆盖 90% 需求、支持私有化部署。剩余 10% 通过 AI 二次开发补齐。

选型原则：能用成熟方案就不造轮子。选 CVAT 不是因为它完美，而是因为它的"不完美"恰好是 AI 可以补齐的部分。

✅ 验收标准定义

📋 每个模块的"完成"定义

  • 中文化：所有可见文字为中文，专业术语（IoU、COCO）保留英文，无中英混杂
  • 权限体系：前端隐藏无权限按钮 + 后端 API 返回 403，双重校验缺一不可
  • 标注工作台：1000 个标注框不卡顿，拖拽/缩放/旋转流畅，撤销/重做正常
  • 审核流程：标注→提交→审核→通过/打回，状态流转正确，打回后可编辑
  • 数据导出：COCO/VOC/YOLO 格式正确，中文标签不乱码
  • 部署：一键启动，域名访问，崩溃自动重启

💡 这些验收标准后来成了每次 AI 对话的"结尾指令"——"做完后帮我验证以上几点"。

🔍 Phase 2：判断"对不对"和"好不好" — 产品思维的核心能力

AI 生成代码后，产品思维最重要的工作不是"看懂代码"，而是判断结果对不对、体验好不好。以下用飞书多维表格中的真实问题截图，展示我是怎么判断的、怎么把问题描述给 AI 的、以及多轮迭代直到满意的过程。

🔄 产品思维驱动 AI 的三步节奏

📋

Step 1：描述需求

用产品语言说清楚"要什么"、"不要什么"、"验收标准是什么"。不说"帮我写个函数"，而说"我需要一个项目级权限系统，标注员只能看到自己的作业"。

🔍

Step 2：判断对不对

部署后实际操作，截图/录屏。看功能是否按预期工作、数据是否正确、流程是否跑通。不需要看懂代码，只需要看"结果对不对"。

✨

Step 3：判断好不好

功能对了之后，还要看体验好不好：操作是否流畅？提示是否清晰？流程是否自然？这是产品思维独有的判断维度。

📌 案例 1：多边形共边与切割 — 从"能用"到"好用"的 5 轮迭代

这是整个项目中迭代次数最多的功能。标注员需要标注紧密相邻的物体（如道路和建筑），要求两个框之间没有缝隙（共边），并且新框能自动切割旧框的重叠部分。AI 第一版实现"能用"，但离"好用"差了很远。

🔵 第 1 轮：提出需求

我给 AI 的描述："需要有选择两个相邻的框进行共边的功能，使两个框之间不会存在缝隙，但它们还是两个独立的框；还需要有切割功能，在已经标注的框上标注新的属性框时，点击切割功能就能将重合的地方切割成新标的框属性，且二者自动共边，不会留有缝隙。"

▲ 飞书表格 Record 23 附件：共边功能需求示意

🟡 第 2 轮：判断"对不对" — 共边后显示有问题

我发现的问题："共边后不要只显示一条边的颜色，两条都要显示。而且现在共边完一个之后，不会让用户选择图像，而是自动跳出选择 1、2 图形就提示共边完成，没有任何自主空间。所以共边完红绿两个框之后，白框就无法再与它们进行共边了。"

▲ 飞书表格 Record 24 附件：共边后只显示一条边的颜色，且无法继续与第三个框共边

产品判断：功能逻辑"对了"（确实能共边），但交互"不对"（用户没有自主权，流程被强制中断）。

🟢 第 3 轮：判断"好不好" — 交互体验优化

我给 AI 的反馈："共边和切割都不要有这种提示框弹出来，界面很乱。共边逻辑不分图像先后顺序，反正点到的两个图像相邻的边贴在一起即可。而切割则默认第一个点击的框对第二个点击的框做切割。选择框时，需要有①②这种序号出现在点击的框位置作为提醒。"

▲ 飞书表格 Record 25 附件：弹窗提示太多，界面混乱

产品判断：功能"对了"，但体验"不好"。弹窗打断操作流、没有序号提示。这些是纯产品体验问题，AI 不会主动想到。

🔵 第 4 轮：切割逻辑修正

我发现的问题："画的一个大框与两个框重叠，切割出来的框形状不是直接按标注原形状再切去重叠部分共边，而是会收缩框体，以及另一个重叠框还是重叠没切割。"

▲ 飞书表格 Record 36 附件：切割后框体收缩变形，且多框重叠时只切了一个

给 AI 的精确描述："切割应该切出这个蓝框的效果，与内部的框完全不重叠，只将中间重叠部分掏空。"

▲ 飞书表格 Record 52 附件：我画的期望效果示意图——告诉 AI "我要的是这个"

🟢 第 5 轮：最终验收通过

经过 5 轮迭代，共边和切割功能最终满足需求：两个框共边无缝隙、切割后形状不变形、多框重叠正确处理、交互流畅无弹窗。最终产出了 817 行的 polygon-operations.ts 组件。

✅ 产品思维的价值：AI 第一版就能"跑"，但只有产品思维能判断"跑得对不对"、"跑得好不好"，并精确描述差距在哪里。

📌 案例 2：帧级工作流 — 判断"流程对不对"

标注平台的核心流程是：领取帧 → 标注 → 提交 → 审核 → 通过/驳回。AI 实现后，我需要判断每个环节的状态流转是否正确。

🔵 发现问题：提交后状态没变

我的判断："帧数在标注点击提交后状态还是'待领取'，正确应该变成'待验收'。然后只有审核账号可以操作标记出错或者打回标注环节。"

▲ 飞书表格 Record 28 附件：提交后状态未从"待领取"变为"待验收"

产品判断：这是典型的"功能做了但流程不对"。AI 实现了提交按钮，但没有联动状态机。

🟡 继续发现：审核无法切换

▲ 飞书表格 Record 20 附件：审核按钮点击无反应

🟢 最终：完整的帧级工作流

经过多轮修复，最终实现了完整的帧级状态流转：unclaimed → annotating → review_pending → reviewing → completed/rejected。

▲ 飞书表格 Record 49 附件：最终实现的帧列表和帧级工作流详情

📌 案例 5：数据导入 — 判断"结果对不对"

🔵 问题：847 帧被拆成 45 个任务（P0）

▲ 飞书表格 Record 81 附件：一个文件夹应该形成 1 个任务，却被拆成了 45 个

🟡 问题：导入后图片不显示（P0）

▲ 飞书表格 Record 85/100 附件：导入 JPG 数据后图像不显示 / 打开是黑色背景

Phase 2 核心总结：

📌 "对不对"= 功能是否按预期工作？数据是否正确？流程是否跑通？→ 用截图/录屏证明"哪里不对"

📌 "好不好"= 操作是否流畅？提示是否清晰？交互是否自然？→ 用产品感觉判断"哪里可以更好"

📌 给 AI 的信息= 截图 + "我做了什么" + "我看到了什么" + "我期望看到什么" → 三要素缺一不可

产品思维不需要看懂代码，但需要看得懂结果。截图和 GIF 是最有力的"需求文档"。

🔥 踩坑经验 — 10 个真实深坑与产品决策

这些不是"小 bug"，而是架构级的坑——每一个都可能导致项目方向调整。产品思维的价值在于：遇到坑时快速判断"绕过去"还是"填上它"。

坑 1Ant Design Table 组件导致页面崩溃已解决
📍 现象尝试用 antd Table 替换卡片布局展示作业列表，页面直接卡死，浏览器弹出"页面无响应"。
🔍 原因Ant Design Table 内部 reconciliation 与 CVAT 渲染管线冲突。尝试 useMemo 转纯对象、移除 BulkWrapper 上下文均无效。怀疑 webpack 下 Table 的 tree-shaking 或循环引用问题。
✅ 产品决策放弃 antd Table，保留原始 Card 布局。Card 能用、稳定、标注员已习惯。如未来需要表格，用原生 HTML table 替代。稳定 > 美观，能用 > 完美。
坑 2Docker 部署 vs virtualenv 部署抉择已解决
📍 现象CVAT 官方推荐 Docker Compose，但服务器需要访问 ossfs 挂载的共享存储。Docker 内访问 FUSE 挂载点需要 --privileged，权限复杂且不稳定。
🔍 原因Docker bind mount ossfs 路径性能差且时常断开；文件所有权与 Django 运行用户不一致；多服务端口映射管理复杂。
✅ 产品决策完全放弃 Docker，用 virtualenv 直接部署。通过 start_services.sh 管理进程，SHARE_ROOT 直接指向 /oss/。官方推荐 ≠ 最适合你。选方案不看"先不先进"，看"稳不稳定"。
坑 3CVAT 前端汉化闪烁问题已解决
📍 现象页面加载时先显示英文再切换中文，闪烁 200-500ms。标注员反馈"每次打开都闪一下英文，很不专业"。
🔍 原因翻译脚本在 DOM 加载后才工作，浏览器已渲染英文。MutationObserver 需要首次渲染完成后才能启动。
✅ 方案脚本头部注入 body { opacity: 0 }，翻译完成后恢复显示。配合 800ms 定时补翻。用户感知："加载完就是中文"。
坑 4Ant Design 组件翻译不生效已解决
📍 现象标准 DOM 文本翻译正常，但 Select、Pagination 等 antd 组件中的文字不被翻译。
🔍 原因antd 组件用特殊 CSS 类包裹文本；MutationObserver 触发后组件重新渲染覆盖翻译；部分组件用 Portal 渲染到 body 之外。
✅ 方案针对 .ant-select-selection-item、.ant-pagination-item 等编写专门翻译逻辑。800ms 定时全量补翻覆盖异步渲染。
坑 5OSS 文件上传超时（504）已解决
📍 现象上传大型数据集时 Nginx 返回 504 Gateway Timeout。
🔍 原因ossfs I/O 延迟比本地磁盘高 5-10 倍；Nginx 默认 proxy_read_timeout 仅 60s。
✅ 方案Nginx: proxy_read_timeout 300s, client_max_body_size 1G。产品层面告知用户"大文件需等待 1-3 分钟"。管理用户预期比优化速度更有效。
坑 6OPA 权限端口冲突已解决
📍 现象CVAT 启动后所有权限操作失败，创建项目、分配任务都报 403。
🔍 原因CVAT 默认 OPA 监听 8181 端口，与 Nginx 生产环境端口完全相同。权限请求发到了 Nginx。
✅ 方案OPA 端口改为 8000。教训：部署前画一张端口分配表。
坑 7CSRF 跨域问题导致所有 POST 被拒已解决
📍 现象通过外部域名访问时，所有 POST 请求被 CSRF 拒绝。IP 直接访问正常。
🔍 原因Django CSRF 默认只信任同源请求。域名访问时端口不同（32654 vs 8181），被判定为跨域。
✅ 方案CSRF_TRUSTED_ORIGINS 添加外部域名；CORS_ALLOW_ALL_ORIGINS = True（内网安全可控）。
坑 8多边形重叠处理的几何计算精度已解决
📍 现象紧密相邻的多边形裁切后出现间隙或微小重叠，放大 400% 后明显。
🔍 原因JavaScript IEEE 754 浮点精度问题；SVG path 孔洞多边形需要特殊编解码；几乎平行的边交点误差被放大。
✅ 方案编写 817 行 polygon-operations.ts；pointsToPathD / pathDToPoints 处理孔洞；epsilon 容差 1e-6。
坑 9独立管理页面与 SPA 路由冲突已解决
📍 现象user-management.html 和 oss-management.html 被 React SPA 拦截，显示 CVAT 的 404。
🔍 原因Nginx try_files $uri /index.html 将所有未匹配请求重定向到 SPA。
✅ 方案Nginx 为独立页面添加优先 location 块；页面设置 __SKIP_CVAT_TRANSLATE__ 跳过汉化。产品决策：低频功能用纯 HTML+JS，不需要 React 全家桶。
坑 10帧级权限与全局权限的协调已解决
📍 现象帧级工作流上线后，"有角色权限但帧不可编辑"和"帧可编辑但无角色权限"的矛盾频出。
🔍 原因CVAT 原有权限基于 Job 粒度；OPA 不适合高频帧级判断；前端 isFrameReadonly() 需综合用户身份、帧状态、工作流阶段。
✅ 产品决策分层控制：OPA 管全局，应用层管帧级。新增 FrameStatus 模型；frame-access.ts 实现综合判断。权限系统不要试图用一套机制解决所有粒度。

📝 踩坑总结：5 个判断原则

1
稳定 > 先进。Docker 是主流，但 virtualenv 在我们环境下更稳定。选方案不看"流不流行"，看"适不适合"。
2
能用 > 完美。antd Table 崩溃？那就不用了。不要为了"更好的方案"引入不稳定风险。
3
分层 > 大一统。OPA 管全局，应用层管帧级，各司其职。
4
部署前画端口表。OPA 8181 和 Nginx 8181 冲突，一张表就能避免。
5
管理用户预期。大文件上传慢是物理限制，加个"预计 1-3 分钟"提示比花 3 天优化更有效。
💡 Phase 5：总结 — 方法论与心得

这个项目验证了一个核心命题：产品思维 + AI = 独立交付能力。关键不在于 AI 多强，而在于产品思维的规划质量决定了 AI 的产出质量。

🧭

规划先行

先画清楚"做什么"再让 AI 动手。没有清晰的需求描述，AI 只会生成"正确但无用"的代码。产品思维的框架能力是 AI 的导航仪。

🔁

小步快跑

不要一次给 AI 一个大需求。拆成小模块，每次验证一个点。100 个小对话 > 1 个大对话。每个模块做完就验收。

🎯

验收驱动

每次对话前先想好"怎么验证做对了"。有验收标准才能判断 AI 的产出是否合格。验收标准就是给 AI 的考试题目。

📝 七条关键心得
1
描述"要什么"比"怎么做"重要 10 倍。"我需要一个项目级权限系统，标注员只能看到自己的作业"比"帮我写一个 Django middleware"有效得多。
2
截图和 GIF 是最好的需求文档。遇到问题不要慌，截图/录屏 + 复现步骤 + 期望效果，这三样给 AI 就能解决 80% 的 bug。就像看医生，你不需要自己诊断，只需要说清楚"哪里疼"。
3
技术选型是产品思维最重要的决策。选 CVAT 而不是自研，省了 3 个月。选型核心：成熟度 × 可定制性 × 部署灵活性。
4
用飞书表格管理问题，形成闭环。每个问题记录优先级、状态、截图、解决方案。100+ 条记录就是最真实的迭代日志，也是给 AI 的"上下文记忆"。
5
接受"停止优化"是一种能力。暗色主题、极端兼容性这些边缘场景，果断标记"停止优化"。产品思维的取舍比执行更重要。
6
让 AI 做全局排查。每次修复时追加"帮我全局排查类似问题"。一次对话解决一类问题，效率翻倍。
7

🔮 可复制的方法论

📋 第一步：定义问题

用产品语言写清楚：谁在什么场景下遇到什么问题，期望方案是什么，验收标准是什么。

🤖 第二步：AI 执行

把需求给 AI，让它生成代码/配置/文档。不需要看懂每一行，只需要验证效果。

🔄 第三步：迭代闭环

发现问题 → 截图描述 → AI 修复 → 验证 → 记录到飞书。循环往复直到验收通过。

核心公式：清晰的产品规划 × AI 的执行力 × 持续的迭代验证 = 独立交付能力
